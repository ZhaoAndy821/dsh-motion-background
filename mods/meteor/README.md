# meteor · 流星雨

深色底上斜向划过的流星群。所有流星互相平行（像从同一个辐射点撒出来），每颗都是
**亮头 + 收束的彗尾**：头部是一个圆形高光，身后拖一条指数衰减的窄带，越靠近头部
越窄、越远越淡，末端平滑收口，头部前方则被短指数砍断。底上还漂着一层缓慢闪烁的
细星点 —— 暗星多、亮星少，半径压在亚像素到 2px，不抢流星的戏。

全部程序化：没有任何纹理采样，随机数由自研的 `fract` 折叠哈希给出（刻意不用
`sin()` 哈希，避免中低精度设备上的平台区条带）。颜色只从 `u_colorFront` 派生，
高光做逐通道软压缩所以核心会自然压白（压白是消色差的，不引入任何新色相）；底色
直接取 `u_colorBack`，不参与压缩，与主题令牌保持一致。

流星头部从画面左外扫到右外，**两端都在画面外**，所以相位回绕的那一瞬间画面上
本来就没有流星 —— 循环天然无缝，不需要额外的淡入淡出遮罩。

## ⚠️ 底色感知（修）

原来这一行是 `fragColor = vec4(u_colorBack.rgb + add, 1.0)`：**加亮**叠加。
深色底上没问题，但**浅色底（白）上会直接饱和到纯白** —— 整帧 `uniqueColors=1`，
画面恒等于底色，等于什么都没画（独立离线审核浅色下 9.7s 内 4 次采样全一样）。

现在按底色亮度选方向：浅色底**按比例压暗**（`base * (1 - amt*0.92)`），深色底维持加亮。
两条路径都保证"没有流星的地方**逐位等于** `u_colorBack`"，所以底纹的透出机制不受影响。
`verify.mjs` 的 E9 就是这条的回归测试（浅色主题下必须 peak > 40 且非底色像素占比 > 0.5%）。

## 设置面板四个旋钮

| 旋钮 | uniform | 效果 |
| --- | --- | --- |
| intensity | `u_intensity` | 整体亮度增益 |
| softness | `u_softness` | 拖尾柔度：越大越宽越糊，越小越像激光细线 |
| noise | `u_noise` | 星空颗粒：密度 + 亮度，0 时星点全灭 |
| shape | `u_shape` | 形态：拖尾长度，0 是短促的弹头，1 是拖得很长的长划 |

## uniform 一览

坐标说明：`q` 是做过纵横比校正的旋转空间，**1 个 q 单位 = 1 个屏幕高度**，
所以下表里的 q 数值乘以屏高就是实际像素占比（1080p 下 1 q = 1080px）。

| 名称 | 类型 | 范围 | 默认 | 视觉作用 |
| --- | --- | --- | --- | --- |
| `u_time` | float | — | 内核注入 | 秒，驱动流星位移与星点闪烁 |
| `u_resolution` | vec2 | — | 内核注入 | 像素尺寸，只用来算纵横比 |
| `u_colorBack` | vec4 | — | 内核注入 | 底色，取其 `.rgb` 直接作背景 |
| `u_colorFront` | vec4 | — | 内核注入 | 唯一色源，流星与星点都从它派生 |
| `u_intensity` | float | 0.0 – 2.0 | 1.0 | 亮度增益。1.0 正常，0 只剩星空，2.0 核心过曝成实心光带 |
| `u_softness` | float | 0.0 – 1.0 | 0.5 | 拖尾高斯半宽 0.0017 → 0.0104 q（1080p 下约 2 → 11 px）。0 是细锐的激光线，1 是发光的弥散带 |
| `u_noise` | float | 0.0 – 1.0 | 0.5 | 星点存在概率 18% → 68%，同时线性缩放星点亮度。0 是纯黑天幕 |
| `u_shape` | float | 0.0 – 1.0 | 0.5 | 拖尾 e 折长度 L = 0.10 → 0.68 q（约屏高的 10% → 68%）；指数尾巴的可辨部分约为 2–3L。0 短促弹头，1 长划 |
| `u_angle` | float | 0.15 – 1.45 rad | 0.55 | 飞行倾角。0.55≈32° 向右下划落；调大更陡，调小更平 |
| `u_speed` | float | 0.2 – 3.0 | 1.0 | 时间倍率。同时影响流星速度与星点闪烁频率 |

范围外的值不会炸：`u_speed` 有下限保护，所有高斯/指数的分母都有正值下限
（`u_softness=0` 时半宽也保留 0.0017 而不是 0），`u_resolution` 任一维为 0 时
纵横比兜底为 1。

## 性能

（headless Chromium + SwiftShader **纯软件光栅**，非 GPU）：

| 项 | 数值 |
| --- | --- |
| 每像素静态指令预算 | **9 次 `exp()`，0 次纹理采样，0 个循环**（源码静态计数） |
| 1920×1080 每帧 | 21.5 ms（≈10 ns/px） |
| 同管线只填纯色（基线） | 1.3 ms/帧 |
| 分辨率放大 4 倍（540p→1080p） | 耗时放大 3.82 倍（理想 4.0） |

SwiftShader 是纯 CPU 光栅，逐像素超越函数吞吐比真实 GPU 低约两个数量级，所以
21.5 ms 是**悲观上界**而不是 GPU 预期值；成本随像素数线性放大也说明它是纯逐像素
开销、没有逐帧固定成本。**我没有在真实 GPU 上验证过**，上面只有软件光栅这一组
可复现数据。

为性能做的取舍：

- **零循环**。每层雨把空间切成"跑道"，但每像素只算它落在的那一条跑道 ——
  所以每像素固定 2 次解析求值，跑道数量只影响画面密度，不影响单像素成本。
- 两个指数合并成一个：`exp(-a/L)·exp(-b/h) ≡ exp(-a/L - b/h)`，画面逐位相同
  （合并前后输出完全一致），每像素省下 2 次 `exp`。
- 星点整体乘 `u_noise`，且在 `u_noise ≈ 0` 时用 `if` 整段跳过；这是 uniform
  条件，全屏同分支，没有 warp 内发散。
- 拖尾带宽从 1.30×收束到 0.22×：远端窄，覆盖的像素少，同时避免长拖尾糊成色带。
- 星点半径压在 1.2–2.1 px（1080p），既不糊成光斑，也不会因为亚像素采样而闪。
- 无 `discard`、无动态数组索引、无 `texture()`，除 `u_resolution` 的除法外没有
  逐像素分支。
